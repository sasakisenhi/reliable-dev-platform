# Feature Specification: Self-Healing Runtime

**Feature Branch**: `001-self-healing`

**Created**: 2026-09-17

**Status**: Ready for Clarification

**Parent Roadmap**: `ROADMAP.md` R1

**Input**: User description: "単一実行インスタンスの喪失後、Developer の復旧判断・操作なしで期待実行数とアプリケーション利用可能性を回復し、その能力を再現可能に検証する。"

## Problem and Hypothesis

**Problem**: 実行インスタンスが予期せず失われた際、その復旧要否の判断および復旧操作が Developer に委ねられている。
これらはアプリケーション機能の開発とは別の環境管理責務であり、Developer の認知負荷を増やす要因となる。

**Hypothesis**: Platform が定義された期待実行数を目標状態として維持し、正常状態からの単一実行インスタンス喪失後に自動で期待状態へ戻せるなら、そのシナリオにおける Developer の復旧判断と操作を不要にできる。
この仮説は、定めた復旧期限内に期待実行数とアプリケーション利用可能性の両方を回復できない場合、または Developer による復旧目的の入力、操作、もしくは直接介入を必要とした場合に反証される。

## Clarifications

### Session 2026-09-18

- Q: 120秒の計測開始点となる「単一実行インスタンスの喪失確認」は、どの観測が成立した時点とするか？ → A: 喪失対象として選んだ個体が稼働中の実行インスタンス集合から外れたことを最初に観測した時点。喪失操作の受理時点は起点とせず、総実行数の減少を観測できなくても対象個体の喪失を確認できれば有効な計測とする。
- Q: 期待実行数の回復後、代表的な利用操作が最初は失敗したものの、120秒以内に現在実行数が期待値と一致している状態で再試行が成功した場合、復旧完了とするか？ → A: 復旧完了とする。最初の失敗だけでは復旧失敗とせず、復旧期限内の再試行を許容する。復旧完了時点は、期待実行数の一致と代表的な利用操作の成功が同時に成立したことを確認した時点とする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 手動復旧なしで利用を再開する (Priority: P1)

Developer として、実行インスタンスが1つ失われても、復旧要否を判断したり復旧操作を行ったりせず、回復後のアプリケーションを利用したい。

**Why this priority**: 環境維持の認知負荷を Developer から Platform へ移し、Developer がアプリケーション開発に集中できるようにすることが、本 Feature の中心価値である。

**Independent Test**: 期待実行数3と代表的な利用操作が正常な状態から実行インスタンスを1つ失わせ、Developer が復旧のための行動を取らなくても、対象個体の喪失確認から120秒以内に実行数が3へ戻り、代表的な利用操作が成功することを確認する。

**Acceptance Scenarios**:

1. **Given** 期待実行数と現在実行数が一致し、代表的な利用操作が成功している、**When** 稼働中の実行インスタンスを1つ選んで失わせ、その個体が稼働中の集合から外れたことを確認する、**Then** Developer による復旧目的の介入なしで、喪失確認から120秒以内に期待実行数の一致と代表的な利用操作の成功が同時に確認できる。
2. **Given** 単一喪失後、代表的な利用操作が一時的に失敗している、**When** 120秒の期限内に利用操作を再試行する、**Then** 期待実行数が一致している状態で利用操作が成功すれば復旧完了となる。

---

### User Story 2 - Self-Healing を自動検証する (Priority: P2)

Platform QA として、この Feature の受け入れシナリオを自動実行し、Self-Healing の成立を再現可能に確認したい。

**Why this priority**: 正常時の確認や主観的な評価だけでは、自動復旧を Platform の品質として主張できないためである。

**Independent Test**: 正常状態の確認から単一実行インスタンスの喪失、復旧完了までを自動で検証し、すべての受け入れ条件を満たす場合にテストが成功し、満たさない場合に失敗箇所を診断出力から確認できることを確かめる。

**Acceptance Scenarios**:

1. **Given** 期待実行数と代表的な利用操作が定義されている、**When** この Feature の自動 E2E 検証を実行する、**Then** 正常状態、選択した個体の喪失、120秒以内の期待実行数の回復、代表的な利用操作の成功、および Developer による復旧介入がないことが確認され、すべてを満たした場合だけテストが成功する。
2. **Given** 自動 E2E 検証で必要な前提条件、喪失観測、または復旧条件を確認できない、**When** テストが終了する、**Then** テストは成功せず、確認できなかった条件を通常の診断情報として示す。

### Edge Cases

- 置換が速く総実行数の減少を観測できなくても、選択した個体の喪失を確認できれば計測を開始する。
- 代表的な利用操作の一時的な失敗だけでは復旧失敗とせず、120秒以内の再試行を許容する。期限内に期待実行数の一致と利用操作の成功を同時に確認できなければ、受け入れ条件を満たさない。
- 正常状態を確認できない場合、または選択した個体の喪失を確認できない場合、その実行では対象シナリオおよび120秒の計測境界が成立したとみなさない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 対象アプリケーションには、検証前に期待実行数と代表的なアプリケーション利用操作が定義されなければならない。検証は、現在実行数が期待実行数と一致し、代表的な利用操作が成功する正常状態を確認してから開始しなければならない。
- **FR-002**: 検証では、稼働中の実行インスタンス集合から喪失対象の個体を1つ選択して識別でき、その個体が稼働中の集合から外れたことを観測できなければならない。
- **FR-003**: 正常状態から実行インスタンスが1つ失われた場合、Platform は現在実行数を期待実行数と正確に一致する状態へ自動的に戻さなければならない。失われた実行インスタンスと同一の個体が戻ることは要求しない。
- **FR-004**: 対象シナリオの復旧では、Developer による復旧目的の入力、操作、または Platform 内部の実行単位への直接介入を必要としてはならない。検証による意図的な単一喪失と観測は復旧目的の介入には含めず、検証中に復旧を促す介入を行ってはならない。
- **FR-005**: 喪失対象として選んだ個体が稼働中の実行インスタンス集合から外れたことを最初に観測した時点を、120秒の計測開始点としなければならない。喪失操作の受理時点は開始点とせず、現在実行数の減少を観測できないことだけを理由に計測を成立しなかったものとしてはならない。
- **FR-006**: 選択した個体の喪失を最初に観測してから120秒以内に、現在実行数と期待実行数の正確な一致、および代表的な利用操作の成功が同時に成立したことを確認しなければならない。この同時成立を確認した時点を復旧完了とし、代表的な利用操作が失敗した場合は期限まで再試行できる。120秒は本番品質の SLO または恒久的な Platform Requirement ではなく、MVP の暫定的な Acceptance Threshold とする。
- **FR-007**: この Feature の自動 E2E 検証は、FR-001 から FR-006 までの受け入れ条件を再実行可能な形で検証し、すべての条件を満たした場合だけ成功しなければならない。成功しない場合は、確認できなかった条件を特定するための通常の診断情報を出力しなければならない。

### Scope Boundaries

**In Scope**:

- 正常状態からの単一実行インスタンス喪失
- Platform による期待実行数への自動復旧
- 期待実行数と代表的なアプリケーション利用操作の成功による復旧完了確認
- 選択した個体の喪失観測を起点とする120秒の復旧期限
- Developer が復旧目的の行動を必要としないことの確認
- 受け入れシナリオを実証する最小限の Feature 固有自動 E2E 検証

**Out of Scope**:

- 再利用可能な Platform E2E 基盤、汎用的な証拠、および障害原因の帰属に関する Capability。これらは `ROADMAP.md` R4 で扱う。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 正常状態から選択した実行インスタンスの喪失を最初に観測してから120秒以内に、現在実行数と期待実行数の正確な一致、および代表的な利用操作の成功が同時に確認される。
- **SC-002**: 単一喪失確認から復旧完了まで、Developer による復旧目的の入力、操作、および Platform 内部の実行単位への直接介入を0件とする。
- **SC-003**: Feature 固有の自動 E2E 検証は、正常状態から復旧完了までの受け入れ条件をすべて満たした実行の100%で成功し、いずれかを確認できない実行の100%で成功せず、確認できなかった条件を診断情報として示す。

## Assumptions

- MVP では期待実行数の検証入力として3を使用する。3は Platform の固定 Requirement ではない。
- 対象アプリケーションは複数の同等な実行インスタンスで動作でき、利用可能性を確認する代表的な操作を持つ。
- 対象環境には期待実行数を満たすための容量がある。
