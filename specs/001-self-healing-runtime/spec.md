# Feature Specification: Self-Healing Runtime

**Feature Branch**: `001-self-healing`

**Created**: 2026-09-17

**Status**: Ready for Planning

**Input**: User description: "単一実行インスタンスの喪失後、Developer の復旧判断・操作なしで期待実行数とアプリケーション利用可能性を回復し、その能力を再現可能に検証する。"

## Problem and Hypothesis

**Problem**: 実行インスタンスが予期せず失われた際、その状態確認、復旧要否の判断、および復旧操作が Developer に委ねられている。
これらはアプリケーション機能の開発とは別の環境管理責務であり、Developer の認知負荷を増やす要因となる。

**Hypothesis**: Platform が定義された期待実行数を目標状態として維持し、正常状態からの単一実行インスタンス喪失後に自動で期待状態へ戻せるなら、そのシナリオにおける Developer の復旧目的の状態確認、判断、操作を不要にできる。
この仮説は、定めた復旧期限内に期待実行数とアプリケーション利用可能性の両方を回復できない場合、または Developer による復旧目的の入力、操作、もしくは直接介入を必要とした場合に反証される。

## Clarifications

### Session 2026-09-18

- Q: 120秒の計測開始点となる「単一実行インスタンスの喪失確認」は、どの観測が成立した時点とするか？ → A: 喪失対象として選んだ個体が稼働中の実行インスタンス集合から外れたことを最初に観測した時点。喪失操作の受理時点は起点とせず、総実行数の減少を観測できなくても対象個体の喪失を確認できれば有効な検証実行とする。
- Q: 期待実行数の回復後、代表的な利用操作が最初は失敗したものの、120秒以内に現在実行数が期待値と一致している状態で再試行が成功した場合、その検証実行をどう判定するか？ → A: PASS とする。最初の失敗だけでは即時 FAIL とせず、復旧期限内の再試行を許容する。復旧完了時点は、期待実行数の一致と代表的な利用操作の成功が同時に成立したことを確認した時点とする。
- Q: 回復中に2つ目の喪失または別種の障害が発生した場合、その原因に応じて検証結果をどう扱うか？ → A: Platform またはその復旧動作に起因すると確認できる追加障害は、有効な検証実行の FAIL とする。Platform から独立した外乱、設定変更、その他の対象外事象による追加障害は品質評価に使用せず、所定の初期条件から再実行する。
- Q: 初期条件不足、対象個体の喪失未確認、または Platform から独立した外乱により品質評価から除外する試行は、どの結果を返すか？ → A: INVALID とし、その理由を記録する。INVALID は PASS / FAIL とは別の結果として扱い、所定の初期条件から再実行する。
- Q: 期待実行数と代表的なアプリケーション利用操作は、誰が定義・維持し、各検証実行へ渡すか？ → A: Developer が期待実行数と代表的な利用操作をアプリケーション契約として定義・維持し、Platform QA が各検証実行で自動利用する。検証ごとの Developer 入力は不要とする。
- Q: 原因を特定できない追加障害が発生した試行は、どの結果として扱うか？ → A: INVALID とし、理由を記録して品質評価から除外し、所定の初期条件から再実行する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 手動復旧なしで利用を再開する (Priority: P1)

Developer として、実行インスタンスが1つ失われても、基盤の状態を調べたり復旧を判断・実行したりせず、回復後のアプリケーションを利用したい。

**Why this priority**: 環境維持の認知負荷を Developer から Platform へ移し、Developer がアプリケーション開発に集中できるようにすることが、本 Feature の中心価値である。

**Independent Test**: 期待実行数3と代表的な利用操作が正常な状態から実行インスタンスを1つ失わせ、Developer が復旧のための行動を取らなくても、120秒以内に実行数が3へ戻り、代表的な利用操作が成功することを確認する。

**Acceptance Scenarios**:

1. **Given** 期待実行数と現在実行数が一致し、代表的な利用操作が成功している、**When** 稼働中の実行インスタンスを1つ失わせ、その個体が稼働中の集合から外れたことを確認する、**Then** Developer による復旧目的の介入なしで、120秒以内に期待実行数の一致と代表的な利用操作の成功が同時に確認できる。
2. **Given** 単一喪失後、代表的な利用操作が一時的に失敗している、**When** 120秒の期限内に利用操作を再試行する、**Then** 期待実行数が一致している状態で利用操作が成功すれば復旧完了となる。

---

### User Story 2 - Self-Healing を再現可能に判定する (Priority: P2)

Platform QA として、正常状態から実行インスタンスを意図的に1つ失わせ、Platform の Self-Healing 能力を客観的な結果として繰り返し検証したい。

**Why this priority**: 正常時の確認や主観的な評価だけでは、自動復旧を Platform の品質として主張できないためである。

**Independent Test**: Developer が維持する同じアプリケーション契約を自動利用して単一喪失を繰り返し検証し、各試行について観測結果から PASS、FAIL、または INVALID のいずれか1つと、その判定根拠が記録されることを確認する。

**Acceptance Scenarios**:

1. **Given** アプリケーション契約と正常な初期状態が確認されている、**When** Platform QA が単一喪失の検証を実行する、**Then** 復旧条件をすべて満たした試行は PASS、満たさない有効な試行は FAIL と、判定根拠が記録される。
2. **Given** 初期条件不足、対象個体の喪失未確認、Platform から独立した対象外事象、または原因不明の追加障害がある、**When** 検証結果を判定する、**Then** 試行は理由付きの INVALID として品質評価から除外され、所定の初期条件から再実行される。
3. **Given** Platform またはその復旧動作に起因する追加障害が確認されている、**When** 検証結果を判定する、**Then** 試行は有効な FAIL と、満たさなかった条件が記録される。
4. **Given** 同じ前提条件、観測対象、および判定境界がある、**When** Platform QA が検証を再実行する、**Then** 検証ごとの Developer 入力なしで同じアプリケーション契約が自動利用され、各試行の結果が記録される。

---

### Edge Cases

- 置換が速く総実行数の減少を観測できなくても、選択した個体の喪失を確認できれば有効な試行として計測を開始する。
- 代表的な利用操作の一時的な失敗は即時 FAIL とせず、120秒以内の再試行を許容する。期限後に回復した場合は FAIL とする。
- 初期条件不足、対象個体の喪失未確認、Platform から独立した対象外事象、または原因不明の追加障害がある試行は INVALID とし、Platform またはその復旧動作に起因する追加障害がある試行は FAIL とする。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 対象アプリケーションには、検証前に期待実行数が定義されなければならない。検証は、現在実行数が期待実行数と一致し、代表的なアプリケーション利用操作が成功する正常状態を確認してから開始し、期待実行数、現在実行数、および個体を識別できる稼働中の実行インスタンス集合を観測できなければならない。
- **FR-002**: 期待実行数と現在実行数が一致する正常状態から実行インスタンスが1つ失われた場合、Platform は現在実行数を期待実行数と正確に一致する状態へ自動的に戻さなければならない。失われた実行インスタンスと同一の個体が戻ることは要求しない。
- **FR-003**: 対象シナリオの復旧では、Developer による復旧目的の介入を必要としてはならず、Platform 内部の実行単位への直接操作を Developer に要求してはならない。Platform QA による意図的な単一喪失と観測は検証操作であり、Developer による復旧目的の介入には含めない。Platform QA は復旧を促す介入を行ってはならない。
- **FR-004**: MVP 検証では、喪失対象として選んだ個体が稼働中の実行インスタンス集合から外れたことを最初に観測した時点を単一喪失の確認時点とする。喪失操作の受理時点は起点とせず、現在実行数の減少を観測できないことだけを理由に試行を無効としてはならない。単一喪失の確認時点から FR-005 の復旧完了時点までの経過時間は120秒以内でなければならない。代表的な利用操作が失敗しても即時 FAIL とせず、期限までの再試行を許容する。120秒は本番品質の SLO または恒久的な Platform Requirement ではなく、MVP の暫定的な Acceptance Threshold とする。実測結果を収集した後、必要に応じて後続の仕様で見直す。
- **FR-005**: 現在実行数と期待実行数の正確な一致と、FR-009 のアプリケーション契約に定めた代表的な利用操作の成功が同時に成立したことを確認するまで、復旧完了として扱ってはならない。復旧完了時点は、その同時成立を確認した時点とする。
- **FR-006**: 検証は、初期の期待実行数と利用可能性、喪失対象の個体、その個体が稼働中の実行インスタンス集合から外れた初回観測時刻、喪失後の実行数、Developer による復旧介入の有無、追加障害の有無と原因、復旧所要時間、最終実行数、復旧後の利用可能性を観測対象としなければならない。
- **FR-007**: 各検証試行は、FR-006 の観測結果から自動的かつ一意に PASS、FAIL、または INVALID のいずれかを返さなければならない。初期条件不足、対象個体の喪失未確認、原因を特定できない追加障害、または Platform から独立した外乱、設定変更、その他の対象外事象に起因すると確認された追加障害がある試行は、INVALID と理由を返して品質評価から除外し、所定の初期条件から再実行しなければならない。INVALID は PASS / FAIL とは別の結果とする。Platform またはその復旧動作に起因する追加障害が確認された試行は有効とし、FAIL と満たさなかった条件を返さなければならない。追加障害が発生していない有効な試行は、Developer による復旧目的の介入を必要とせず、実際にも介入がなく、FR-004 および FR-005 を満たした場合に限り PASS とし、それ以外は FAIL と、満たさなかった条件を返さなければならない。
- **FR-008**: 検証は、同じ前提条件、単一喪失の定義、観測対象、判定境界を用いて再実行できなければならない。
- **FR-009**: Developer は期待実行数と代表的なアプリケーション利用操作をアプリケーション契約として定義・維持しなければならない。Platform QA は同じ契約を初期条件の確認と復旧判定に自動利用し、検証ごとの Developer 入力を要求してはならない。

### Scope Boundaries

**In Scope**:

- 正常状態からの単一実行インスタンス喪失
- Platform による自動復旧
- 期待実行数への回復
- 復旧結果の観測
- Self-Healing 能力の再現可能な検証
- Developer が手動復旧を必要としないことの確認

**Out of Scope**:

- 実行インスタンスを収容するホストまたは実行基盤自体の障害
- 実行基盤全体の障害
- ネットワーク分断（Network Partition）
- 永続ストレージ障害
- Platform から独立して発生する複数障害からの復旧
- 不健全な実行インスタンスへのトラフィック制御
- 復旧処理中の継続的なサービス可用性の保証
- バージョン更新時の段階的な切り替え
- 更新中の無停止性
- 本番環境向け高可用化
- Developer Portal や Platform API

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 正常状態から選択した実行インスタンスの喪失を最初に観測してから120秒以内に、現在実行数と期待実行数の正確な一致、および代表的な利用操作の成功が同時に確認される。
- **SC-002**: 単一喪失確認から復旧完了まで、Developer による復旧目的の入力、操作、および Platform 内部の実行単位への直接介入を0件とする。Developer が状態を閲覧しなかったこと自体は品質条件に含めない。
- **SC-003**: 検証試行の100%が PASS、FAIL、または INVALID のいずれか1つを返し、FAIL には満たさなかった条件、INVALID には品質評価から除外する理由が記録される。
- **SC-004**: 同じ前提条件、単一喪失の定義、観測対象、および判定境界を変更せずに検証を再実行でき、再実行のたびに結果が記録される。
- **SC-005**: Platform QA が実行する検証の100%が Developer の維持するアプリケーション契約を自動利用し、検証ごとの Developer 入力を0件とする。

## Assumptions

- MVP では期待実行数の検証入力として3を使用する。3は Platform の固定 Requirement ではない。
- 対象アプリケーションは複数の同等な実行インスタンスで動作でき、利用可能性を確認する代表的な操作を持つ。
- 対象環境には期待実行数を満たすための容量がある。
